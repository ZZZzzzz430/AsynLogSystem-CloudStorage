# 配置加载改动纠错记录

日期：2026-09-23。已修复源码并完成下述验证。

## 主要问题

### 1. 数据读进 content，却解析空的 str

位置：[日志 Util.hpp](../../log_system/logs_code/Util.hpp)，`JsonData` 构造函数。

原改动声明 `std::string str;`，但文件读取写入的是 `content`。随后 `UnSerialize(str, &root)` 解析空字符串，因此即使配置文件合法也会抛解析失败异常。

修复：删除多余的 `str`，将实际读到的 `content` 传入解析函数。

排查经验：沿着数据流检查“谁写入哪个变量、下游读取哪个变量”，两个变量类型相同不代表内容相同。

### 2. 修正了同名函数，但不是实际被调用的那个

项目有 `storage::JsonUtil` 和 `mylog::Util::JsonUtil` 两套 JSON 工具。

用户将 `src/server/Util.hpp` 中的成功返回值改为 `true`，这个修改本身正确，已保留。但日志配置初始化调用的是 `log_system/logs_code/Util.hpp` 中的解析函数，它在成功时仍返回 `false`。

修复：将日志版本的成功路径也改为 `return true`。解析失败仍返回 `false`。

这两个问题相互独立：只修输入变量仍会误报失败；只修返回值仍会解析空字符串。

### 3. 同一内容准备解析两次

原改动在带判断的解析调用之后，又保留一次不检查结果的 `UnSerialize(content, &root)`。原错误路径下走不到这里；修正前面问题后，它会成为重复解析。

修复：只保留一次解析，并检查它的返回值。成功后才读取字段。

### 4. throw 后面的 perror 永远不会执行

`throw` 会立即沿调用栈寻找异常处理，紧随其后的 `perror(NULL)` 不会运行。

修复：移除不可达语句，把配置路径放入异常消息。统一使用已有的 `config_path` 变量读取配置，避免声明变量后仍重复硬编码路径。

### 5. 头文件依赖和诊断细节

- 在日志 `Util.hpp` 自身加入 `<stdexcept>`、`<memory>`、`<sstream>`，明确它所用类型的声明来源。不能靠其他文件碰巧先包含它们；尤其在入口文件 `Service.hpp` 之后包含 `<stdexcept>`，不能保证此前处理的头文件获得声明。
- `CheckConfigFile()` 成功时补上路径输出。
- 修正提示中的 `Chenk`，给工作目录提示加分隔符，删除异常输出中的重复换行。
- 保留用户的 `main()` 异常处理结构，它的位置与本次配置失败处理目标一致。

## 修复后的调用逻辑

```text
main
→ log_system_module_init
  → GetJsonData → JsonData 构造函数
    → GetContent(&content, config_path)
      失败：抛读取错误
    → UnSerialize(content, &root)
      失败：抛解析错误
      成功：返回 true，读取配置成员
  → 配置成功后才创建线程池与日志器

异常 → main 的 catch → 输出错误及配置路径 → return 1
```

## 实际验证

编译：在 `src/server` 执行 `make gdb_test`，成功。

使用独立临时目录 `/tmp/asynlog-config-review-28ali2tk`，没有修改原始配置、存储数据或启动正常 HTTP 服务。

临时 `config_probe.cpp` 直接包含日志工具头文件并调用真实解析器及 `GetJsonData()`，不是模拟实现。

| 验证 | 实际结果 |
|---|---|
| 解析器接收合法 JSON | 返回 true，解析内容正确 |
| 解析器接收非法 JSON | 返回 false |
| 配置加载探针读取原始配置 | 退出 0，读取到 `buffer_size=10000000`、`thread_count=3`、`flush_log=2` |
| 配置加载探针读取语法错误、空文件、缺失文件 | 三项均退出 1 |
| 完整服务入口读取语法错误配置 | catch 输出配置解析错误及路径，退出 1 |
| 完整服务入口读取空配置 | catch 输出配置解析错误及路径，退出 1 |
| 完整服务入口遇到缺失配置 | 存在性检查阻止初始化，退出 1 |

探针输出中会有一条故意输入非法 JSON 产生的解析诊断，这是负向测试的预期输出，不代表正常配置验证失败。

## 范围与后续

本次完成“读取 → 解析 → 失败传递”的纠错，没有增加完整字段类型、取值范围校验。合法 JSON 中的错误业务值仍属于待办。没有执行 HTTP 上传下载回归，因为未修改 HTTP 处理逻辑。

需要记住的三个检查习惯：先追变量的数据来源，再确认命名空间和实际函数，最后分别验证成功与失败路径。

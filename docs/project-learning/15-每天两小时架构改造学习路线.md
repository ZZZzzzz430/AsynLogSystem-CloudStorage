# 15：每天两小时，逐步贴合 14 架构的学习与改造路线

制定日期：2026-10-22。依据：[14：Qt 与存储服务接口架构参考](14-Qt与存储服务接口架构参考.md)。

目标：沿着当前 Qt 客户端与 libevent 存储服务，每天完成一个足够小的工程改动，形成“理解需求和源码 → 自己编写 → 编译运行 → 正常/故障测试 → 解释结果”的循环，逐步达到 14 文档的模块边界和接口约定。

这是学习日程与任务划分，本次未代写这些任务的核心实现，也没有把计划中的功能标为完成。

## 1. 工期、起点和执行规则

建议 **64 个学习日，每日最多 2 小时，计划投入 128 小时**。另预留 8 个机动学习日，处理依赖安装、未定位的问题和复测；它们没有额外新功能。按每天学习计算，主计划约 9 周；每周 5 天则约 13 周，机动时间另计。这是任务预算，不是必须在某个日期完成的承诺。

14 文档的“半天～一天”等是功能实施粗估。本计划把独立理解、编写、排错与验收都算进两小时，因此重新拆分。用 D01、D02 表示学习日，不绑定日历，中间休息后接着当前任务继续。

本次开始查看的起点：HEAD `0da0ee3`；`Client/ApiClient` 仍只有 `testConnection`，正式 Qt 工程没有上传、下载、账户、模型与队列。14 配套的独立传输示例已经存在，但它不是你独立完成正式集成的证据。旧 SetContent 错误返回、上传元数据错误链、下载查询失败处理等问题仍能在当前代码找到。

整理期间发现你已调整 `Client/CMakeLists.txt`：当前源码已统一查找并链接 Qt6 Widgets/Network，保留 C++17 与自动生成设置。**D01 的这部分代码不需要重写，接着做配置解释、新构建与连接测试验收即可。** 已有构建产物变化不代替实际结果核验；本次未改动你的 CMake 或构建目录。

执行规则：

1. **一天只有一项主任务。** 正常功能与它的错误路径属于同一项；不在完成后自动开下一天的新模块。
2. **两小时到点就保存现场。** 记录做到哪里、失败现象、下一步，不通过熬夜补齐；次日先完成剩余验收，再顺延后续任务。
3. **代码未通过，不按日期自动毕业。** 单纯“读过”“照抄能编译”“助手示例跑过”分别记录，不能等同于自己掌握。
4. **助手先给任务、边界、提示、验收；你写核心实现。** 你提交改动和结果后，再评审源码、数据流、线程、错误处理和测试证据。需要完整示范时，再按你的明确要求给出。
5. **每项只读用得上的源码。** 不为了开始上传先完整学完日志、线程池、网络库和数据库；缺失知识结合当前问题补齐。
6. **每阶段保持可运行。** 小步提交，保留前一版本的正常行为；不先创建全部空类，再隔很久才联调。
7. 正式联调使用独立实验数据。Windows Qt 和 Linux 服务分别构建；环境问题优先消耗机动日，不算作业务功能完成。

## 2. 每天固定的 120 分钟

| 时间 | 内容 | 当天要留下什么 |
|---|---|---|
| 0～10 分钟 | 复盘上次结论，预测本次行为 | 一句话目标、1～2 个待验证判断 |
| 10～30 分钟 | 定向阅读 1～3 个函数或一个新类型 | 简短调用链；数据、对象寿命、线程归属 |
| 30～85 分钟 | 自己实现当天改动并编译 | 可检查的最小改动；遇错先定位，避免同时换多个变量 |
| 85～110 分钟 | 至少一个正常实验、一个故障/边界实验 | 输入、实际结果、退出码/HTTP 状态、文件或日志证据 |
| 110～120 分钟 | 整理结果和口头解释 | 修改点、未解决问题、当天状态；能解释一个设计选择 |

有些天主要是复现、测试或重构。实现时间可以用于编写测试驱动、失败注入或整理复现脚本，但仍要运行验证。编译排错超过预算时，可缩小当天代码范围，不能删除测试环节来假装完成。

测试采用最便宜的有效方式：早期允许手工 HTTP/摘要比对，协议与存储逻辑稳定后再保留针对性自动检查。不为简单控件文字变化写一整套测试，也不把 Mock 当真实服务联调。

## 6. 如何判断一天完成

当天至少留下三类证据：

1. **改动证据**：具体文件/函数、为什么这样改；无代码修改的实验日留下可重复的脚本或实验记录。
2. **运行证据**：重新构建/运行结果、一个正常与一个故障/边界输入、实际输出、文件/数据库/日志状态。
3. **理解证据**：能沿调用链解释输入如何变成结果，指出当前线程、对象寿命或共享资源；不要求每天把所有知识点重讲一遍。

建议状态采用：未开始 → 已布置 → 编写中 → 待验收 → 已通过；另记“源码已评审”和“实际运行已验证”，不要互相替代。测试受环境阻挡时标明待验证，后续依赖它的安全切换不算完成。

未来每日结果优先补在本篇末尾；出现值得单独分析的问题再按编号新增专题，并更新索引。不提前生成 64 个空文档，也不改写历史笔记里的完成状态。

你提交当天结果时可用这个格式：

```text
学习日：Dxx
用时：不超过 120 分钟；超出范围的工作下次继续
目标与预测：
改动文件/函数：
正常测试：输入 → 实际输出 → 证据
故障/边界测试：输入 → 实际输出 → 证据
我的解释：调用链、线程/寿命/失败处理中的一个关键点
没完成/不确定的地方：
```

评审时重点看三个问题：“这个边界为什么放这里？”“失败有没有继续向上报告？”“哪份证据证明判断？”发现阻塞点先缩小问题，不直接把后续所有实现贴出来。

# 13：Qt 客户端主线升级实施方案

> 2026-10-27 用户明确将数据库选型改为 **MySQL**，并要求只给框架与挖空练习。本文中的 SQLite 是历史方案；当前数据库接口、状态与练习以 [18：MySQL 接入框架与挖空练习](18-MySQL接入框架与挖空练习.md) 为准，不将 SQLite 特有配置照搬到 MySQL。

日期：2026-10-20。状态：方案已整理，尚未创建客户端、修改协议或迁移数据。用户本次明确将方向改为“Qt 桌面客户端为主，服务端功能与架构升级为支线”，本篇取代 12 中“先强化服务端、之后再 Qt”的推进顺序。历史成果保留，不再把源码追踪任务作为新功能开发的前置验收。

## 1. 最终交付与第一版范围

交付一个能实际演示的 C++/Qt 云盘桌面程序，连接现有 Linux/libevent 服务端：

- 服务地址设置、连接状态、注册/登录/退出。
- 当前用户文件列表：名称、大小、上传时间、刷新。
- 文件上传、下载、进度、明确的失败提示与重试入口。
- 用户之间的文件隔离，服务重启后账户与文件记录仍可恢复。
- CMake 构建、关键自动化测试、部署和运行文档。

第一版用 Qt Widgets + Qt Network + C++17；保留现有 libevent、JsonCpp 和异步日志。新版本文件元数据及账户使用 SQLite；密码使用 libsodium 密码哈希接口。首版仅开放普通存储，保留旧压缩功能但不暴露到新版 UI；完整 Range、分享、删除、云同步、回收站与大规模并发以后再加。

先保持现有 1MiB 文件上限，客户端提前检查、服务端最终检查，UI 明示限额。这样既能尽早完成传输体验，又不把大文件流式接收和并发内存治理混在首轮。放宽限制应另立里程碑。

按每天约 2～3 小时估算，安排 5 周左右；时间取决于 Qt 环境、目标平台和实现反馈。按交付验收推进，不按日期强行叠功能。开发时间预算约 60% 客户端、25% 支撑 API、15% 构建与测试。

## 2. 当前基础与需补的差距

源码检查：旧 `/upload` 接受原始二进制正文，FileName 是 UTF-8 文件名的 Base64，StorageType 为 low/deep；`/` 返回 HTML；下载按文件名组成 URL；DataManager 使用 URL 到元数据的 map 和 storage.data，没有 owner 字段。

因此 Qt 可以直接复用旧上传下载完成首个演示，但不能通过抓取 HTML 当作长期列表协议，也不能仅增加登录窗口就认为完成了用户隔离。

本环境 pkg-config 未找到 Qt6Core/Network/Widgets 和 sqlite3；这只表明当前发现路径没有对应包，不等于其他机器或 Qt Creator Kit 没安装。尚未选择客户端最终运行系统。默认先实现开发机可运行版本，服务端保持 Linux；若 Qt 在 Windows，允许只构建 client target。安装和打包在执行阶段按目标平台确认，本次未安装依赖。

## 3. 架构：客户端提出需求，服务端按需抽取

```text
Qt Widgets
  LoginDialog / MainWindow / TransferPanel
        ↓ 信号与操作
  AuthController / FileController / TransferManager
        ↓
  ApiClient（QNetworkAccessManager、统一 JSON/状态码解析）
        ↓ HTTP JSON / 文件字节
  libevent 入口 → Router → AuthHandler / FileHandler
        ↓
  AuthService / FileService
        ↓
  UserRepository / SessionStore / FileRepository → SQLite
  FileStorage → 文件目录
        ↓
  原异步日志（先复用）
```

UI 不直接拼 HTTP 和 SQL；ApiClient 不操作控件；Handler 负责协议到业务参数的转换；Service 处理业务；Repository 只处理记录；FileStorage 处理实际文件。第一周只实现需要的类，目录结构不是开工时一次性建齐的要求。

建议逐步形成：

```text
项目根目录/
  CMakeLists.txt
  CMakePresets.json
  client/                         # 新增，不覆盖旧 src/client
    CMakeLists.txt
    src/main.cpp
    src/ui/{LoginDialog,MainWindow,TransferPanel}.{hpp,cpp}
    src/network/ApiClient.{hpp,cpp}
    src/controller/{AuthController,FileController}.{hpp,cpp}
    src/model/FileListModel.{hpp,cpp}
    src/transfer/TransferManager.{hpp,cpp}
  src/server/
    CMakeLists.txt
    Test.cpp / Service.hpp          # 过渡入口，逐步缩小职责
    http/{Router,RequestContext,JsonResponse}.{hpp,cpp}
    handlers/{AuthHandler,FileHandler}.{hpp,cpp}
    services/{AuthService,FileService}.{hpp,cpp}
    repositories/{Database,UserRepository,FileRepository}.{hpp,cpp}
    auth/SessionStore.{hpp,cpp}
    storage/FileStorage.{hpp,cpp}
  tests/{server,client}/
  docs/api-v1.md
```

没有需求时不建立空抽象接口或通用框架。新写的普通类默认声明/实现分离；模板和必要的 inline 留在头文件。旧 Service 先保留其余路径，只把新 API 相关逻辑抽出来。日志库中存在头文件定义和全局变量，不能直接让多个 cpp 都包含旧整套实现；迁移相关模块时同步处理单一定义和依赖边界，以真实多翻译单元链接检查 ODR 问题。

## 4. Qt 侧的实现规则

选择 Widgets 是为了尽早获得桌面文件列表和表单，不另开 QML 学习线。列表使用 QTableView + QAbstractTableModel；一期只需名称、字节数/格式化大小、时间列，不先引入复杂分页 UI。

ApiClient 持有一个 QNetworkAccessManager，正常网络请求异步完成，不能在 UI 槽里用阻塞等待或嵌套事件循环。上传以 QFile 作为正文设备，确保文件在 reply 完成前存活；接 uploadProgress，但进度到 100% 仍需等待服务器成功响应才标“已完成”。

下载在 readyRead 中分块写 QSaveFile，检查写入结果，响应状态及长度检查通过后 commit，失败不提交。errorOccurred 与 finished 统一收口一次，reply 用 deleteLater；窗口关闭/退出时明确取消和对象生命周期。已关闭页面的回调不能继续访问失效控件。

小文件传输不为每个请求新建 QThread。以后增加大文件 hash 等 CPU 工作时，再移到受控工作线程，QObject 的归属与 UI 更新仍遵守线程边界。首版 TransferManager 最多同时运行 2 个传输，其余排队，避免一次选文件后无限发请求。

任务状态：Queued → Running → AwaitingResponse → Succeeded/Failed/Cancelled；每条任务有独立 id。网络错误、HTTP 业务错误、磁盘写失败、未登录与用户取消分别展示。401 返回登录状态时保留必要失败提示，不自动无限重试上传。

取消下载可以清理未提交文件；取消上传只保证客户端停止传输，服务端可能已经保存成功，需刷新列表确认，不能承诺远端回滚。

## 5. 先约定 API，再写两端

命名空间 `/api/v1`。登录及元数据为 UTF-8 JSON，上传与下载为二进制；不引入 multipart 解析器，避免与旧原始 body 协议混用。以下是拟定契约，当前代码尚未提供。

| 方法/路径 | 请求/用途 | 成功 | 关键失败 |
|---|---|---|---|
| GET /api/v1/health | 客户端连接检查 | 200 | 服务不可达由 Qt 网络层报告 |
| POST /api/v1/auth/register | username、password JSON | 201 | 400、409、限频 429 |
| POST /api/v1/auth/login | username、password JSON | 200，token、expires_at | 401、429 |
| POST /api/v1/auth/logout | Bearer token | 204 | 401 |
| GET /api/v1/me | 当前用户 | 200 | 401 |
| GET /api/v1/files?limit=50&offset=0 | 当前用户记录，固定排序 | 200，items、total | 400、401 |
| POST /api/v1/files | 原始 body、FileName: Base64(UTF-8 名称) | 201，文件对象 | 400、401、413、500 |
| GET /api/v1/files/{id}/content | 按 id 下载，检查 owner | 200，二进制 | 401、404、500 |

文件对象：id、name、size、created_at。时间统一 UTC ISO 8601；id 当不透明字符串使用，不传绝对磁盘路径。未知文件和其他用户的文件统一返回 404。同名上传保留两条不同 id 的文件，避免悄悄覆盖；UI 可显示时间区分，重命名以后再做。

JSON 错误统一如 `{"error":{"code":"FILE_SAVE_FAILED","message":"文件保存失败"},"request_id":"..."}`；状态码与业务 code 都要检查。返回必要诊断，不回传密码、token、SQL 或绝对路径。204 不返回 JSON；Qt 不对二进制下载或空响应强行解析 JSON。

注册用户名首版限制为 3～32 个 ASCII 字母/数字/下划线并统一小写；密码不自动 trim，长度范围与口令哈希库输入上限一致并明确文档化。文件名支持 Unicode，但必须校验分隔符、NUL、空名及字节长度，真实磁盘键独立于显示名。

## 6. Router：承担分发，不承担整个业务

拟定注册风格：`router.add(Method::Get, "/api/v1/health", handler)`；后续支持 `/api/v1/files/{id}/content` 参数段。Handler 接收 RequestContext，其内容为请求、解析后的 path、参数、认证上下文；只在本次同步回调有效。

先实现 exact route，再增加一个按段匹配的参数模板；不写通用正则路由框架。精确路由优先，重复/歧义注册在启动时报错；同路径方法错误 405 并提供 Allow，未知路径 404。匹配使用解析后的 path，不把 query 当路径一部分；路径分段和 percent decoding 统一规则，拒绝非法编码及编码分隔符造成的歧义。

libevent 的 generic callback 保留，但只调用 Router::dispatch。这是对现有网络库的适配，Router 不创建新线程、不保存裸 req 等待后台任务。异常应在 HTTP 边界转换为一次 500；开始发送二进制响应后不能再次发送 JSON 错误。

## 7. 登录必须带上文件归属

采用 SQLite 而不是继续扩展 storage.data：账户唯一性、按 owner 查询、记录持久化和事务都需要明确数据模型。建议表：

```text
users(id PK, username UNIQUE, password_hash, created_at)
files(id PK, owner_id FK, original_name, storage_key UNIQUE,
      size, created_at, state)
sessions(token_hash PK, user_id FK, expires_at)
```

使用参数绑定 SQL、显式 schema_version 迁移；SQLite 连接按初始化启用外键。初版数据库操作仍归当前服务执行上下文，不把同一个连接任意跨线程共享。

密码用 libsodium 的密码哈希与验证 API，不存明文，不以普通 SHA-256 替代密码哈希。不先实现 JWT：使用密码学安全随机 token，建议 32 字节随机数编码；服务端仅存 token 摘要、用户和过期时间，注销删除会话。Qt 首版仅内存保存 token，不做自动登录；密码不持久化，日志不记录认证正文或 Authorization。

认证查询得到 user_id 后注入上下文，绝不相信客户端传入的 owner_id。所有文件列表、下载和上传都经过认证及 owner 检查。旧 `/`、`/upload`、`/download/...` 在认证版本切换时默认禁用；否则旧下载路径会绕过权限。匿名旧接口只能作为显式本地 legacy 演示模式，不能与多用户正式模式同时开放。

上传使用服务器生成的 storage_key，先写临时文件，检查 write/flush/close，再提交可用记录；文件与 SQLite 无跨资源原子事务，需要定义 pending/ready 状态、失败清理和启动时对账。UI 成功只在 ready 后报告。第一版不追求断电零丢失，但至少不能吞掉错误或把失败记录当作可下载。

旧数据不删除，也不自动归属第一个注册用户。新版本使用独立数据库和数据目录；需要迁移时做显式导入命令，要求指定目标用户、备份和 hash 校验，单独验收。新版 API 不同时从 JSON 与 SQLite 两套权威索引读取。

MVP 在本地/开发网络运行。跨公网部署前使用 HTTPS 入口；限频、会话过期和跨用户拒绝属于登录里程碑验收。密码哈希本身昂贵，初版同步实现会占用事件线程，需记录此限制；若验收发现登录影响传输，定向增加有界认证任务执行与事件线程完成通知，不能靠 UI 异步掩盖服务端阻塞，也不能改弱哈希参数来冒充优化。

## 8. CMake 渐进迁移

新增根 CMake，提供 BUILD_SERVER、BUILD_CLIENT、BUILD_TESTING 开关，避免 Windows 构建客户端时解析 POSIX 服务端依赖。设 C++17、目标级 include/link、Debug/Release Presets，产物放 build/，运行数据独立于构建目录。

服务端先把现有 Test.cpp + base64.cpp 链接成功，查找 Threads、Libevent、JsonCpp、bundle；bundle 无完整仓库构建脚本，明确导入库路径及依赖版本，不默默依赖某台机器的系统安装。旧 Makefile 暂时保留，CMake 回归通过后变为构建包装或标记 deprecated；不要使用原 clean 清掉用户数据。

客户端 find_package(Qt6 REQUIRED COMPONENTS Widgets Network)，使用 Qt 的 CMake 初始化与自动 moc/ui，测试引入 Qt Test。不要让服务端依赖 Qt，不把两端绑定在一个巨大的 target 中。

现有配置按 cwd 查找，迁移时先通过 CMake 明确工作目录保持兼容，随后增加 `--config` 和数据根目录参数，统一所有配置路径；不能只复制二进制到 build/ 就假定它能启动。

预期命令示意，需在实现对应 target 后使用：

```bash
cmake -S . -B build/server -DBUILD_SERVER=ON -DBUILD_CLIENT=OFF
cmake --build build/server
cmake -S . -B build/client -DBUILD_SERVER=OFF -DBUILD_CLIENT=ON
cmake --build build/client
ctest --test-dir build/server --output-on-failure
```

## 9. 里程碑：每一步都有能点开的版本

| 顺序/预算 | Qt 主线成果 | 服务端支线 | 验收门槛 |
|---|---|---|---|
| M0：1～2 天 | CMake 创建窗口、服务器地址输入、日志提示区 | 旧服务 CMake target，可保留 Makefile | 两端分别构建；窗口能启动；旧上传下载不退化 |
| M1：2～3 天 | 文件选择、上传进度、按已知文件名下载、成功/失败状态 | 尽量复用旧接口，修挡住演示的返回值错误 | 不接 JSON 列表也能真实传一个二进制文件；失败不显示成功；UI 不冻结 |
| M2：约 1 周 | QTableView 文件列表、刷新、按 id 下载 | Router、JSON 文件 API、SQLite FileRepository/FileStorage | 本地临时单用户演示；唯一 id，同名不覆盖，重启列表恢复 |
| M3：约 1 周 | 注册/登录/退出、登录状态与过期提示 | AuthService、账户/会话、owner 检查、关闭旧匿名入口 | A/B 用户相互看不到/下载不到文件；过期与注销生效；退出清理旧用户列表 |
| M4：约 1 周 | 队列、双传输、取消、失败重试体验、窗口生命周期 | 上传失败/临时文件恢复、按需要抽取服务类 | 网络中断、服务重启、写盘失败、关闭窗口均可恢复；不重复提交/回复 |
| M5：2～3 天 | 桌面包、演示数据、使用文档 | CTest、API 契约、部署说明 | 干净环境复现；两用户端到端演示；问题/限制记录完整 |

M2 使用显式本地开发身份及独立空数据目录，不宣称已实现安全多用户；M3 替换临时身份并关闭旁路。未进入 M3 时不开放公网。

每个里程碑只进行对应抽取：例如 M2 拆 Router/FileService，M3 才拆 Auth，不先重排整个日志库。若时间不足先延迟皮肤、图标、自动更新、删除和压缩，不削减错误处理和跨用户权限验收。

## 10. 测试与完成定义

- Router：精确/参数匹配、query、405 Allow、404、歧义注册、非法路径编码。
- 文件业务：保存失败能传出、同名不同 id、临时文件不进入列表、重启恢复；输入/下载 SHA-256 比较，hash 首先用于测试，不提前扩展产品功能。
- 认证：重复注册、错误密码、过期/注销、SQL 参数处理、A 不能读取 B 的文件、旧匿名路径不可绕过。
- Qt：连接拒绝/超时、HTTP 400/401/413/500、非 JSON 错误、目标目录不可写、取消后恢复、退出页面不访问失效对象；文件列表模型用 Qt Test 覆盖。
- 端到端：两账户分别上传同名不同内容文件，列表各自独立，下载摘要一致，服务重启后再次登录与下载正确。

每次功能提交有一个可操作界面或可调用 API、有针对性的测试和简短变更说明，不再以阅读多少代码作验收。核心模块单测与 HTTP 集成测试区分；Mock 不能替代真实服务联调。

## 11. 第一批工作：只做 M0 + M1

先落地五项：根 CMake 开关；Qt 主窗口；ApiClient；文件选择与旧 /upload 上传；基于已知文件名下载并验证字节。不先做登录界面假数据，也不先重写 Service。

M1 的下载 URL 对文件名正确编码，原 FileName 头使用 UTF-8 Base64；上限/空体规则与当前服务一致。旧 HTML 列表此时不解析，M2 再以 JSON 正式实现。

完成后应能演示：选择一个小文件 → 看到传输进度 → 服务端确认成功 → 保存下载文件 → 内容一致；停掉服务后再次上传显示错误，窗口仍可操作。这个结果作为下次评审起点，之后才开 M2。

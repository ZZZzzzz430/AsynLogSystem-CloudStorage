## 后部分：阶段 4 · 学习块 1——请求为何一起变慢

时间盒 60～90 分钟。只回答一个问题：**一个 HTTP 回调阻塞，会不会让其他请求也等它？** 本次通过小实验和耗时观测验证，不把整个 HTTP 模块搬到线程池。

### 1. 为什么需要事件循环，为什么仍会阻塞

事件循环让一个线程响应多个连接的网络事件，避免每个连接都创建一个线程。但回调是在这个线程上运行的普通 C++ 函数，库不会自动把压缩、文件写入、日志等待放到别的线程。

当前源码路径：

```text
Test.cpp: main → 创建 t1 → join
t1: service_module → Service::RunModule
  → event_base_new / evhttp_new / evhttp_set_gencb
  → event_base_dispatch
  → Service::GenHandler
     ├─ Upload → SetContent 或 Compress → DataManager::Insert
     ├─ ListShow → GetAll → HTML
     └─ Download → 查元数据 → 可能解压 → open / evbuffer_add_file
```

同一时刻多个客户端可以连接，但当前业务回调由一个事件循环线程执行。慢上传阻塞期间连接还可能进入内核队列，不能把“TCP 已连接”当作“业务回调已开始”。

### 2. 源码范围与共享资源

- [Test.cpp](../../../src/server/Test.cpp)：`service_module` 的栈对象 Service，t1 的创建与 join。
- [Service.hpp](../../../src/server/Service.hpp)：`RunModule / GenHandler / Upload / ListShow`；本次不深入 Range。
- [AsyncLogger.hpp](../../../log_system/logs_code/AsyncLogger.hpp)：`serialize` 的 `future.get()`，以及 `Flush → Push`。
- [CliBackupLog.hpp](../../../log_system/logs_code/backlog/CliBackupLog.hpp)：`start_backup` 中同步 connect/write。

RunModule 的 base/httpd 是 HTTP 线程创建的局部指针，事件循环使用它们；每次 req 由 libevent 提供，不是可任意捕获到线程池的永久对象。全局 data_ 和注册日志器是共享资源；本次保持单 HTTP 线程模型，不引入新的请求所有权和并发存储问题。

请求 body 已在 evbuffer 中，Upload 复制到 std::string，再调用文件工具；元数据另写 storage.data。业务文件写入发生在 t1，日志文件输出发生在 AsyncWorker 后台。分别标清楚“哪个文件的 IO”，不要笼统说 IO 已异步。

### 3. 三个阻塞点要区分

| 阻塞点 | HTTP 线程做什么 | 证据应看哪里 |
|---|---|---|
| 业务文件操作/压缩 | 直接运行 SetContent、Compress、元数据持久化 | HTTP 栈和文件系统调用、CPU |
| 日志反压 | Info → Flush → Push 等空间 | HTTP 栈中的条件变量等待，后台消费栈 |
| 重要日志备份 | Error/Fatal 的 serialize 提交任务后 future.get | HTTP 等 future；备份线程在 connect/write |

备份重连最多尝试五次，但没有应用层明确总期限，每次 connect 耗时由环境影响；本地端口未监听通常立即拒绝，不能把“没启动备份服务”直接当作稳定长时间阻塞实验。仅从代码可知 future.get 会等待任务，不宣称本次已实测其延迟。

PushFor 目前只提供新接口，AsyncLogger::Flush 仍调用原 Push，HTTP 日志并没有自动获得超时策略。

### 4. 正常实验与安全故障实验

沿用 [06 的独立目录步骤](06-upload-roundtrip-and-validation.md#4-独立实验目录)，端口 18081，复制最新调试二进制。正常实验先请求列表，记录状态码与首字节时间：

```bash
curl --max-time 10 -sS -o /dev/null -w 'code=%{http_code} start=%{time_starttransfer} total=%{time_total}\n' http://127.0.0.1:18081/
```

故障采用受控暂停，不需要磁盘满或大文件。**仅在实验构建临时加入**：Upload 校验成功之后，使用标准错误打印一个明确的“delay entered”标记，再 `sleep_for(2s)`。不要放在配置初始化或日志后台；它模拟 HTTP 回调被耗时工作占住，不宣称是真实磁盘性能。

在独立目录提交合法小文件，StorageType=low、Base64 文件名使用新的名称，具体 curl 沿用 06。看到 delay entered 后，另一个终端立即请求列表；对照没有上传时的基线。预期列表首字节时间增加，剩余延迟取决于第二次请求发出的时刻；不要求恰好 2 秒。

再同时发 2、6 个列表请求观察：它们可以一起等当前回调，不能据此解释成服务器出现了 6 个 HTTP 工作线程。实验后移除临时 sleep，重新编译并回测基线，留下修改前、暂停期间、恢复后的三组记录。不将 sleep 留在最终业务代码中。

### 6. 本次小改造：统一记录回调耗时

在 GenHandler 增加一个作用域计时器，目标是所有分支、包括提前 return，都产生一条记录：路径、回调耗时、当前线程 ID。普通记录用 INFO，超过 100ms 用 WARN；不用 ERROR/FATAL，以免测量自己触发同步备份等待。

范围只涉及 Service.hpp 和一个小计时辅助类。使用 steady_clock，计时器保存拥有所有权的 path 字符串，不保留 req 指针；构造放在路由分派前，析构覆盖返回路径。路径解析之前的时间可以明确不纳入；阈值无需扩展成配置框架。

析构中日志失败不能向外抛异常，也不能递归记录错误；可捕获后用标准错误做简短兜底。这次还不改变原业务日志调用策略。计时结果只代表被计时的回调区间，不包括客户端上传全程或响应字节全部发送完成；异步日志最后一次输出本身也不应计入先前已计算的区间。

验收：正常列表有记录；2 秒暂停上传有慢回调 WARN；非法上传提前返回也有记录；移除 sleep 后重新回测。正常低耗时不是保证所有机器上都低于阈值，按实测值判断。编译调试版和普通版，保持数据目录独立。核心计时实现留给用户编写。

### 7. 先形成三个回答，再向前走

1. 网络库处理事件，为什么同步压缩会拖慢其他请求？
每个事件循环管理多个连接，但是事件循环线程一次只能执行一个回调，在处理文件压缩等 IO 资源操作时往往耗时更久，并且独占线程，使得线程不能返回事件循环处理其他已就绪的 HTTP 请求。可以将这些耗时较久的相应放到工作线程进行异步处理，任务完成后进行通知并进行相应。
2. 日志已经异步，HTTP 为什么还可能等它？备份线程池能否消除 future.get 的等待？
第一种情况是 缓冲区已满出现的生产者反压，HTTP 循环需要等待空闲缓冲区容量进行推送；备份任务交给线程池执行，但是回调调用了 future.get() 则仍然会同步等待结果。两者共同点在于在事件循环中进行等待，但是条件不同。
3. 回调耗时、首字节时间和请求总时间分别包含什么？哪份证据证明阻塞发生在 HTTP 线程？
回调耗时是服务器业务回调自身的执行时间，首字节时间是从客户端开始请求到收到相应第一个字节，请求总耗时是从开始请求到本次响应传输结束。

    其次是调试当中，通过 gdb 进行调试，发现 bt ；info threads 等确认线程所在。

## 阶段 07：HTTP 事件循环与阻塞机制——测试总结

### 一、测试目标

理解 libevent 单线程事件循环的工作机制，分析同步业务操作、异步日志和 `future.get()` 对 HTTP 请求处理的影响，并通过 GDB、curl 验证真实项目中的 HTTP 调用链。

### 二、测试过程与结果

**1. HTTP 上传与文件完整性测试**

使用 `mktemp -d` 创建临时测试环境，通过 `export` 保存路径变量，使用 `cp -a` 复制项目文件。

通过 `dd` 创建 64KiB 测试文件，使用 curl 向 `/upload` 发送 HTTP 请求。

测试结果：

- HTTP 状态码：200
- curl 请求总耗时：约 20.45ms
- 上传文件大小：64KiB
- 目标文件成功生成
- `cmp` 比较未发现文件内容差异

结论：本次小文件上传闭环正常，但不能仅凭 HTTP 200 证明所有内部操作都正确。

**2. GDB 线程与调用栈测试**

通过 GDB 在 `Service::Upload()` 设置断点，成功命中 HTTP 上传回调。

使用 `bt` 查看调用栈，确认以下调用关系：

```text
service_module()
    ↓
Service::RunModule()
    ↓
libevent 事件循环
    ↓
Service::GenHandler()
    ↓
Service::Upload()
```

通过 `info threads` 观察到服务器存在多个线程，其中执行 `Upload()` 的是 GDB Thread 7，对应 Linux LWP 1142847。

结论：已经证明上传回调由 libevent 事件循环调用，不能因为服务器存在多个线程，就认为每个 HTTP 请求都有独立的工作线程。

目前还需要进一步验证 `SetContent()` 的实际执行线程和耗时。

### 三、核心知识理解

**1. 并发不等于多线程，也不等于并行。**

单个事件循环线程可以管理多个 TCP 连接，但无法同时执行多个普通同步回调。如果一个回调长时间不返回，其他请求的回调就可能延迟执行。

**2. 阻塞的是当前线程，而不是整个进程。**

当 HTTP 线程执行 `sleep_for()`、`future.get()` 或等待条件变量时，该线程无法继续执行后续 HTTP 回调，但其他工作线程仍然可以运行。

**3. 异步执行不代表调用方一定不会阻塞。**

异步日志虽然由后台消费者负责写盘，但缓冲区满时，生产者调用 `Push()` 仍然可能等待空间。

备份任务即使提交到线程池，如果 HTTP 线程立即调用 `future.get()`，仍然需要等待任务结果就绪。

**4. 真正的异步 HTTP 设计需要将耗时业务与事件循环解耦。**

基本流程：

```text
HTTP 事件循环接收请求
    ↓
解析请求并保存必要上下文
    ↓
提交耗时任务到工作线程
    ↓
HTTP 回调返回，继续处理其他请求
    ↓
工作线程完成任务
    ↓
通知 HTTP 事件循环
    ↓
发送响应并清理资源
```

不是所有 HTTP 回调都需要工作线程。快速操作可以直接执行，耗时压缩、同步文件 I/O 等操作则需要根据性能需求选择适当的异步处理方式。

**5. 区分三种耗时指标。**

- 回调耗时：HTTP 回调进入到返回所经历的时间。
- TTFB：客户端发起请求到收到响应首字节的时间。
- 请求总耗时：客户端发起请求到响应接收完成的时间。

客户端请求耗时很长，不一定说明它自己的业务函数执行很慢，也可能是等待事件循环处理。

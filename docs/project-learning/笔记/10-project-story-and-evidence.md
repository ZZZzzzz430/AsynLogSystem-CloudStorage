## 2. 先用真实架构做底稿

```text
主线程：日志配置/备份池/日志器初始化 → 元数据加载 → 启动 HTTP 线程 → join
HTTP 线程：libevent 分派 → 上传/列表/下载 → 同步文件操作与元数据更新
                            ↓ 日志格式化、Push
日志工作器：双缓冲交换 → 输出器 → 文件输出
备份线程池：ERROR/FATAL 的 TCP 备份任务
            ↑ 调用线程 serialize 中的 future.get 仍等待它
```

查证位置：[Test.cpp](../../src/server/Test.cpp)、[Service.hpp](../../src/server/Service.hpp)、[AsyncLogger.hpp](../../log_system/logs_code/AsyncLogger.hpp)、[AsyncWorker.hpp](../../log_system/logs_code/AsyncWorker.hpp)。默认日志器和命名日志器各有工作器，不能把整个服务说成“只有一个后台线程”；HTTP 单事件线程也不等于整个进程单线程。

数据主线：请求体 → libevent evbuffer → string → 普通写盘或压缩写盘 → StorageInfo → DataManager 内存表与 storage.data。日志是另一条支线，格式化与复制发生在调用线程，输出主要由后台完成。

## 4. 核心案例：64 字节缓冲为何拒绝合法消息

优先讲这个案例，因为有一次错误方案、稳定复现与修正后回归，比罗列很多功能更有证据。

按下面顺序自行写 400～600 字：

1. 原问题：固定模式下单条消息大于总容量，等待条件永远不能满足。
2. 第一版偏差：按剩余空间立即拒绝，删掉等待，导致正常积压也拒绝合法消息。
3. 定位：受控回调占住消费者，另一块 Buffer 写入 48 字节后再写 32；总容量 64、剩余 16，32 应等待，不应拒绝。
4. 修正：先按 Capacity 拒绝超大消息，其余按 WriteableSize 等待；持锁检查、等待与追加，交换后通知生产者。
5. 证据：32/64/65 边界、拒绝后继续可用、受控暂满等待、2/6 生产线程字节计数；后续 PushFor 增加可配置等待期限与明确结果。
6. 限制：Accepted 是进入缓冲区，不是 fsync 完成；计数正确不单独证明全部内容和顺序；现有 HTTP 日志仍走原 Push，没有自动使用 PushFor。

对应源码是 AsyncWorker 的 Push/PushFor/ThreadEntry 和 Buffer 的 Capacity/WriteableSize/Swap。线程是谁、锁保护什么、条件变量等什么，必须能回到代码解释。不要把这个案例称为全系统“日志零丢失”。

最后回答四个追问，先不给完整标准答案：

1. 磁盘越来越慢时，业务线程最终会在哪里等待？为什么增加 Buffer 只能延迟问题出现？
最终在 Push 等待缓冲区的容量处，扩大 Buffer 只能短暂应对，面对长期吞吐量不平衡背压问题不可避免。可以通过丢弃低优先级日志，
2. PushFor 超时没有追加数据，上层应怎么处理？你现在是否已经把它接到了 HTTP 日志调用？
超时表示没能入队，上层不能认为写入日志文件。可以对于普通日志进行丢弃，保证 HTTP 服务不会因此阻塞和一直重传。关键日志可以通过分流等更可靠的备份策略。
3. 上传返回 200，但元数据文件写失败，重启会怎样？读写锁是否能提供事务保证？
先判断响应 200 是在提交任务后返回还是写入文件后返回、或者是校验文件后。如果是设计层面的缺陷重启不能改变，读写锁不能提供，因为读写锁只负责数据同步资源交互，对于文件完整没有帮助。
4. 你独立写了什么、评审帮你修了什么、哪些测试自己真正运行过？给出一个具体例子。

第 3 题先沿 [DataManager.hpp](../../src/server/DataManager.hpp) 的 Insert → Storage 和 Service::Upload 阅读：当前 Storage 对 SetContent 失败记录日志后仍返回 true，Upload 也未检查 Insert 返回值。这是源码发现，尚未在本块复现或修复；不要把“知道风险”说成“已解决一致性”。

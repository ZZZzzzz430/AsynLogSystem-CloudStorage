## 三、项目真正的架构

项目是基于开源学习代码研究和改进的 C++ 文件存储服务，包含浏览器上传、列表、下载、普通/压缩存储、JSON 元数据和异步日志。它没有用户权限隔离，也不是分布式存储或已完成生产加固的服务。

核心代码导航：

| 位置 | 主要职责 |
|---|---|
| [Test.cpp](../../../src/server/Test.cpp) | 启动检查、日志与备份池初始化、元数据加载、HTTP 线程 |
| [Service.hpp](../../../src/server/Service.hpp) | 路由、上传校验、列表、下载、回调计时 |
| [DataManager.hpp](../../../src/server/DataManager.hpp) | URL 索引、读写锁、JSON 持久化和启动恢复 |
| [存储 Util.hpp](../../../src/server/Util.hpp) | 文件读写、压缩解压、存储侧 JSON 工具 |
| [AsyncLogger.hpp](../../../log_system/logs_code/AsyncLogger.hpp) | 日志格式化、备份任务等待、提交与实际输出回调 |
| [AsyncWorker.hpp](../../../log_system/logs_code/AsyncWorker.hpp) | 生产等待、PushFor、双缓冲交换和停止 |
| [AsyncBuffer.hpp](../../../log_system/logs_code/AsyncBuffer.hpp) | vector 字节存储、容量、读写位置及扩容 |
| [LogFlush.hpp](../../../log_system/logs_code/LogFlush.hpp) | 标准输出、文件、滚动文件及刷盘 |

### 启动与线程

```text
主线程 main
  → 工作目录/配置存在性诊断
  → 日志配置读取与解析
  → 创建备份线程池、构建注册日志器
  → 创建 DataManager，加载元数据
  → 创建 HTTP 线程 t1 → join

HTTP 线程 t1
  → service_module → RunModule → event_base_dispatch
  → GenHandler → Upload / ListShow / Download

每个 AsyncWorker 的后台线程
  → 等数据 → 锁内交换 → 锁外输出 → Reset

备份线程池
  → ERROR/FATAL 的 TCP 备份任务
```

默认日志器和命名日志器各自创建工作器。配置备份线程数为 3 时，源码创建路径通常推导出主线程、HTTP、两个日志线程、三个备份线程共 7 个；实际身份以线程栈为准，不把 GDB 编号写成永远固定的线程标识。

### 两条数据流

```text
业务：请求体 evbuffer → string → 普通写入/压缩写入
    → StorageInfo → 内存 table_ → JSON storage.data
    → 后续按 URL 查询 → 普通读取/解压 → HTTP 输出

日志：调用线程格式化 → string → Push/PushFor → 生产者 Buffer
    → Swap → 消费者 Buffer → RealFlush → 输出器
    → fwrite → 按配置选择 fflush / fsync
```

Swap 交换存储与读写位置，不逐字节复制日志；但此前格式化、构造字符串、复制入 Buffer 都有成本。正文日志记录的线程 ID 是产生日志的线程，不是最终写文件的线程。

## 四、已经完成的核心改造与验证

### 1. 启动配置：让失败停在初始化边界

存在性检查失败由 main 返回 1；真正读取与解析仍必须各自处理错误。修复过“数据读取到 content，却解析空 str”和“改了另一命名空间的同名解析函数”等问题，说明定位必须追踪实际数据和调用目标。

日志配置加载失败抛异常，入口捕获并输出路径；初始化不应继续进入线程池创建。05 保存了合法、非法、空、缺失配置的运行记录，并有正常首页及二进制上传下载一致性测试。完整字段类型和数值范围仍是待办，不等于合法 JSON 就业务有效。

### 2. 上传入口：先拒绝，再产生业务副作用

已实现方法、非空体、1MiB 上限、必要请求头、存储类型、解码后文件名的校验；失败回复并立即返回，成功才继续复制正文、写文件和更新索引。方法错误为 405，过大为 413，其余对应非法输入为 400。

06 的完整实验主要依据用户完成反馈；05 有独立基础二进制闭环，bug记录 中又独立验证了缺头上传 400、GET 上传 405 等路径。不能把这些不同批次的证据合并成“全部边界今天重新测过”。请求体长度检查发生在库接收正文之后，也不能称作流式上传限额。

### 3. 固定日志缓冲：区分永远放不下与暂时放不下

这是目前最完整的定位与改造案例：

- 原问题：总容量 64，单条 65，等再久也不能满足空间谓词。
- 第一版错误：按剩余空间拒绝并删除等待，使正常积压也抛异常。
- 稳定复现：消费者受控暂停，生产者已有 48、剩余 16，再提交合法的 32，错误版本立即拒绝。
- 修正：超过总容量才拒绝；未超过总容量则按剩余空间等待。检查、等待、追加遵循同一锁协议。
- 回归：32/64/65 边界、拒绝后可用、暂满等待、2/6 生产线程通过；修正后暂满案例消费 144 字节，2/6 线程分别消费 16000/48000 字节，无拒绝。

Buffer 扩容也修正了“等于剩余空间仍扩容”和“一次扩容仍不足”的问题，并检查长度计算/增长溢出。对应探针验证过大消息内容；没有因此证明所有极限分配都安全。

### 4. PushFor：给等待空间增加明确结果

新增成员接口使用 steady_clock 截止时间与条件变量谓词，返回 Accepted、TimeOut、Stopped、TooLarge；实际枚举拼写为 TimeOut，文档示例中 TimedOut 是同一语义。

已独立验证容量边界、零/负期限、满缓冲超时、释放后成功、超时无追加、超时后恢复、停止唤醒、混合生产者和增长模式。用户原慢消费探针也验证了约 200ms 的等待及最终 136 字节消费。

期限针对等待缓冲空间，不是覆盖加锁、调度、复制的硬实时保证。当前 AsyncLogger::Flush 仍调用原 Push，HTTP 日志尚未自动采用 PushFor；超时后丢弃、重试或降级的策略仍需上层决定。

### 5. 停止与回调计时

停止流程先设置停止状态、唤醒等待者，再 join 后台；后台消费已接受数据后退出。受控实验通过停止唤醒、128 字节排空、顺序重复 Stop、停止后拒绝等检查。回调不返回时 join 仍会等待；notify 不能中断回调内部的 IO。

ScopeTimer 使用 steady_clock，持有路径副本，析构覆盖正常返回、提前返回和异常展开；100ms 以上记录 WARN，否则 INFO。修复类名拼写、try/catch、日志接入及路径处理后，调试版和普通版编译、独立 HTTP/计时测试通过。计时器 catch 做兜底，但不保证日志等待一定很短。

## 五、必须能准确解释的工程边界

| 容易混淆的说法 | 本项目应如何解释 |
|---|---|
| 异步日志等于业务不阻塞 | 格式化、锁、Buffer 反压仍在调用线程；ERROR/FATAL 还会 future.get |
| 一个事件循环等于只能有一个连接 | 可管理多个连接，但普通同步回调仍占用同一个 HTTP 线程 |
| 多个 curl 等于多个 HTTP 工作线程 | 请求可并发到达，当前回调仍在单事件线程执行 |
| Info 返回等于交换/落盘 | 只保证正常路径已复制入生产者 Buffer，不保证消费或持久化 |
| fwrite 等于数据稳定落盘 | 还涉及 C 库缓冲、内核缓存与设备同步；错误返回也需要检查 |
| 读写锁等于文件事务 | 锁保护内存 map，不保证文件、索引、JSON 同步提交 |
| 回调耗时等于请求总时间 | 回调只覆盖被计时区间；TTFB/总时长还含排队、网络和传输等 |
| 200/206 等于完整功能正确 | 200 仍需内容与索引证据；206 仍需正确 Range 解析、区间内容和响应头 |
| 计数一致等于所有日志完整有序 | 计数只证明总量，内容和顺序需要额外验证 |

资源观察应围绕假设：GDB 的 bt/info threads 定位线程与调用路径，ps -T 看线程状态，ss 看监听，strace 关联线程、fd 和系统调用，cmp/哈希比较内容。低 CPU 也可能是严重等待，监听正常也可能业务停滞。

## 六、10 中现有回答的反馈

第 1 题对缓冲积压和长期速率不平衡的解释正确。补充：丢低优先级日志是可选策略，需要定义丢弃计数与可观察性；当前实现没有因此自动具备分级丢弃。

第 2 题正确说明超时不等于落盘，提出普通日志丢弃、关键日志分流的方向。但还应明确回答：**目前没有把 PushFor 接入 HTTP 日志调用**；关键日志备份也不等于可靠投递。

第 3 题应更贴合当前代码：普通上传先写业务文件，再改内存索引、尝试保存 JSON，随后返回 200。当前 Storage 对 SetContent 失败仅记录日志仍返回 true，Upload 也不检查 Insert。于是进程运行时文件可能可查，重启从旧的或不完整 JSON 恢复后，新文件可能没有索引，列表/下载不可用；文件仍在磁盘也不代表可由服务查到。读写锁无法提供跨这几步的事务。

第 4 题及完整口述尚未填写。用户独立实现、助手评审修正、助手补测、用户实验应分别说明。不会因有示范文案就将个人表达任务标为完成。

继续采用“先走主线、后回头复习”，每次只完成一个小闭环；下面是建议安排，不是已经开始或完成的新任务。

| 顺序 | 时间盒 | 做什么 | 最小交付 |
|---|---|---|---|
| 1 | 45～60 分钟 | 收尾项目表达 | 90 秒个人介绍、3 分钟缓冲区案例、个人贡献回答；明确哪些测试自己执行 |
| 2 | 2～3 小时 | 只做元数据保存失败的错误传播 | 复现写失败却 200，追 Storage→Insert→Upload 的返回链，修正并验证成功/失败；明确不等于完成事务 |
| 3 | 1～2 小时 | 下载不存在时只回复一次 | 查索引失败立即 404，其他失败及时 return；正常下载与未知 URL 回归 |
| 4 | 60～90 分钟 | 集中回补最重要证据 | 一份日志线程交接栈、一份慢回调/Stop 栈、一组 HTTP 延迟对照，不重写已通过代码 |
| 5 | 半天以内 | 整理可复现交付 | 将关键探针、启动命令、输入、预期、实际退出码整理到仓库；核对简历措辞 |

第二项的首轮目标仅是让保存失败真实传到响应边界。失败时是否回滚内存、清理业务文件，以及临时文件加 rename 的原子替换，必须单独界定，不要把“返回 500”称为一致性已经解决。进一步实现时再逐步设计恢复策略。

更长期再按需要选择：解压临时文件隔离、元数据原子持久化、Range、带请求生命周期管理的工作线程异步处理、真实负载性能测量。不要一次引入所有改造，也不必等到这些全部完成才开始投递和面试练习。

当前最值得巩固的是：**能把一个具体问题的现象、线程、数据、条件、修改和验证讲成一条有证据的因果链。**

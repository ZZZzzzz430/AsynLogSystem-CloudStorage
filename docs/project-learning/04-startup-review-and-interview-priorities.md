## 2. 第一项练习掌握了什么

### 真实项目中的位置

`src/server/Test.cpp` 是服务端启动入口，不是独立单元测试。`test` 和 `gdb_test` 都由这份入口构建，后者增加调试信息。

```text
main                                        主线程
→ PrintStartupInfo                          新增：观察当前工作目录
→ CheckConfigFile × 2                       新增：配置不存在则提前退出
→ log_system_module_init
  → 加载日志配置
  → 创建备份线程池
  → 创建、注册日志器
→ new DataManager
  → 加载存储配置和元数据
→ 创建 HTTP 线程
→ 主线程 join 等待
```

你新增的代码是服务的启动检查，能够在缺少文件时阻止后面的初始化。

### 已经练到的基础

- 定义函数、传入参数、使用局部变量、按返回值选择分支。
- 普通函数 `return false` 只返回失败结果；`main()` 中 `return 1` 结束程序并报告退出状态。
- 相对路径根据进程工作目录解析，与可执行文件的位置无关。
- 初始化存在依赖：存储模块的初始化函数会调用日志接口，因此日志器要先注册。
- 日志器尚未创建时，启动错误可以通过 `std::cerr` 报告。
- 用断点和系统调用记录说明程序实际执行到哪里，而不是只凭报错猜原因。

可以记住这一段项目表述：

> 我在服务入口加入了工作目录诊断和配置存在性检查。从错误目录启动时，相对配置路径失效；我通过文件打开的 ENOENT 和调用栈定位，再让入口在检查失败时返回非零退出码，避免继续初始化。这个改动目前只检查存在性，不保证配置可读或内容有效。

这是准确的小改造经历，适合作为排障例子，不应包装成整个项目的核心创新。

## 3. 第二项练习要理解什么，但目前不能声称已完成

配置加载有四个不同层次：

```text
路径存在 → 能打开并读完 → 是合法 JSON → 字段含义可用于当前程序
```

例如文件存在但内容为 `{`，存在性检查会成功，解析却会失败；`thread_count` 为字符串或为 0，又分别属于类型和取值问题。

这项改造要练的是错误如何穿过函数边界：

```text
读取 / 解析 / 校验失败
→ 配置构造失败并抛异常
→ main 捕获
→ 输出具体原因
→ 返回 1
```

需要知道：

- 构造函数中的 `return;` 只是提前结束构造函数体，不会自动表示对象创建失败。
- 抛异常会使构造失败；调用方需要合适的处理边界。
- 先检查字段类型和范围，再转换到 `size_t` 或 `uint16_t`，避免负数或过大值转换后失真。
- 存在性检查与实际打开之间，文件仍可能发生变化，所以不能省略实际读取时的错误处理。
- 配置加载发生在线程池创建之前，应该在这个边界阻止非法配置继续流入线程和 Buffer。

求职优先时，可以将完整字段校验留到后续。若要收尾，只做一个短闭环：修正解析返回值、处理解析失败、入口报告并退出，验证合法与非法 JSON 两种情况即可。不要让完整配置框架成为阅读日志核心的前置门槛。

## 4. 当前应掌握的 Linux 与调试知识

命令中的 PID 用实际进程号替换；GDB 中可用 `info inferiors` 查看被调试进程号。以下表格是速查清单，不表示每项都已经实操。

| 目的 | 命令 | 看什么、能说明什么 |
|---|---|---|
| 确认终端当前目录 | `pwd` | 解释从当前终端启动时相对路径的基准 |
| 确认运行中进程的目录 | `readlink /proc/PID/cwd` | 验证进程实际 cwd；不要把另一个终端的目录当作它的目录 |
| 确认运行的二进制 | `readlink /proc/PID/exe` | 防止调试或启动了旧副本 |
| 查看退出状态 | 程序结束后立即执行 `echo $?` | 0 通常表示成功，非零表示失败；1 的含义由程序约定 |
| 跟踪配置文件访问 | `strace -f -e trace=openat,newfstatat -o /tmp/startup.trace ./gdb_test` | 路径、系统调用返回值、ENOENT 或 EACCES |
| 筛选配置访问 | `rg 'config.conf|Storage.conf' /tmp/startup.trace` | 将启动阶段的文件操作与源码对应 |
| 查看调用关系 | GDB：`bt`、`frame N` | 当前线程调用栈；不是所有线程的执行历史 |
| 观察变量和返回值 | GDB：`p variable`、`next`、`step`、`finish` | 输入是什么、执行哪个分支、函数实际返回什么 |
| 查看线程 | GDB：`info threads`、`thread apply all bt` | 将当前栈与其他线程区分；详细分析留给日志模块 |
| 查看异常抛出 | GDB：`catch throw` | 停在异常抛出时，通过调用栈定位来源 |
| 确认是否监听 | `ss -ltnp` | Local Address:Port 与所属进程；权限不足时进程信息可能不完整 |

补充几个容易混淆的点：

- `ENOENT` 表示路径中的目标或某级目录不存在，不能仅凭它判断是权限问题；权限不足常见为 `EACCES`。
- `std::filesystem::exists()` 返回 false 不能等同于所有形式的检查失败，需要同时观察错误码。
- `std::cerr` 对应标准错误通道，shell 可用 `2>` 重定向；它不依赖项目日志器。
- 普通文件路径查询会涉及内核文件系统接口，但不是“每查一次都必然读取物理磁盘”，缓存会影响实际 IO。
- GDB 单步会改变线程运行时序，不适合作为真实性能测量；`strace` 也会带来额外开销。
- `main()` 返回 1 是受控退出，与崩溃、信号终止不同。

现在不必系统学习 systemd、所有 Linux 工具或文件系统内部实现。遇到具体项目问题，再补对应知识。

## 5. 学习是不是太慢：是，原来的粒度应调整

此前每个小知识点都拆成一次练习，适合刚开始建立动手习惯；继续这样推进，会让大量时间消耗在入口和工具函数上。配置模块对理解初始化有价值，但不足以代表这个项目最核心的设计。

现在的目标调整为：能跑通、能讲清主链路、能深挖一到两个核心点、能展示自己验证过的改动。基础通过真实问题补齐，不要求读完每个类才允许往后走。

## 6. 这个项目最值得形成的三种能力

### 能讲清真实架构

- HTTP 服务使用一个事件循环线程；并不是一个请求对应一个业务线程。
- 文件写入、压缩和解压在 HTTP 回调中执行，会占用事件循环线程。
- 日志格式化发生在调用线程；后台线程负责消费双 Buffer 并输出。
- 备份线程池用于重要日志 TCP 备份；调用处的 `future.get()` 仍会等待。

这些是源码结构结论，还需要通过实验把它们变成你自己的证据。

### 能深挖异步日志

重点围绕：锁保护什么、条件变量等待什么、为什么交换后再写文件、生产过快如何反压、磁盘变慢怎样影响业务、停止时如何处理剩余数据。

先选一个可控问题做完整改造即可，例如“固定 Buffer 模式下单条日志超过容量时如何处理”。具体实验与修改策略进入该模块时再布置，避免现在同时开多个任务。

### 能准确表达自己做过的工作

可以说自己阅读、调试和修改了什么；保留原项目来源。没有测过的吞吐量、不丢日志保证、完整断点续传和完整线程安全，都不能写成已实现能力。

项目介绍可以按“业务用途 → 真实线程模型 → 自己的改动 → 验证证据 → 当前限制”组织，不需要背诵所有类名。

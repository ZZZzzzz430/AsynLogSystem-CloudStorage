# Qt 注册与登录：对照改动学习、逐步验证

编写日期：2026-11-13。针对本次新增和修改的 Qt 客户端代码。

**学习目标：能沿着一次注册请求找到每一步代码，解释等待、成功、失败、关闭四种情况，并亲手验证。**

这份手册使用目前工作区的实际函数和测试名称。第 23 份文档保留作功能概览，这份按“看一小段代码 → 说清作用 → 验证现象”的方式学习。本轮只新增文档、更新索引，不替你修改业务代码。

## 0. 怎么读，才不容易被细节绕晕

不用从构造函数第一行一直读到文件最后。分三遍：

| 遍数 | 只读哪些内容 | 读完能做到什么 |
|---|---|---|
| 第一遍，约 20 分钟 | 第 1～5 节 | 说清“检查 → 提交 → 等待 → 结果”的流程 |
| 第二遍，约 30 分钟 | 第 6～11 节 | 解释超时、关闭、回填、登录门禁 |
| 第三遍，约 30～45 分钟 | 第 12～16 节 | 自己运行测试、观察变量、记录证据 |

第一遍可以暂时跳过布局、样式和 QPointer 的细节。你最先要找到的三处是：

1. `RegisterDialog::submit()`：用户点注册之后做什么。
2. `ApiClient::registerUser()`：怎样联系服务器。
3. 注册窗口中连接 `registrationFinished` 的 lambda：收到回复后做什么。

全文代码块有两种：标注“实际代码”的摘自工作区；标注“简化流程/反例”的仅用于理解，不要求复制替换。代码行号会随着你的注释变化，优先用函数名搜索。

### 1.1 先把三个角色认清

| 角色 | 通俗理解 | 不由它决定的事 |
|---|---|---|
| RegisterDialog | 注册表单：收集输入、显示提示 | 不能凭输入正确就宣布服务器注册成功 |
| ApiClient | 联系服务器：发送、等回复、解释回复 | 不直接创建主窗口 |
| LoginWindow / main | 回填登录、接收认证结果、切换窗口 | 测试连接成功不能当作登录成功 |

```text
点击注册
  → RegisterDialog 检查填写内容
  → ApiClient 向服务器发送请求
  → 服务器回复
  → ApiClient 通知 RegisterDialog
  → 失败：恢复表单；成功：回到登录页
```

这里有两个不同的“注册成功”信号：

- `ApiClient::registrationFinished(bool, message)`：网络层报告本次操作是否成功，成功和失败都会报告。
- `RegisterDialog::registrationSucceeded(username)`：窗口只在确认成功后通知登录页回填用户名。

不要仅因为名字相似就把它们当成同一个信号。

## 2. 模块一：打开注册窗口

**一句话：原来的“注册暂不可用”提示，被替换成打开真实注册表单。**

在 `LoginWindow::onRegisterClicked()` 找到实际代码：

```cpp
if (loginPending_ || connectionPending_) return;
if (registerDialog_) {
    registerDialog_->raise();
    registerDialog_->activateWindow();
    return;
}
QUrl url;
if (!readServerUrl(url)) return;
auto *dialog = new RegisterDialog(url, this, authenticationTimeoutMs_);
registerDialog_ = dialog;
dialog->setAttribute(Qt::WA_DeleteOnClose);
```

按顺序理解：

1. 正在登录或测试连接时，不同时启动注册操作。
2. 已有注册窗口时，把已有窗口显示到前面，避免开出多个表单。
3. 检查服务器地址，避免把请求发向明显错误的地址。
4. 创建注册框，保存指针，配置关闭后自动删除。

最后用 `dialog->open()` 打开。它会立即返回；当前是窗口模态对话框，父登录页暂时不能操作，但注册框本身仍能输入、移动、返回和关闭。不要把“异步打开”理解成“父子窗口一定都能同时点击”。

### 2.1 为什么有些变量成了类成员

原来注册按钮只是 `setupUi()` 的局部指针。本次变成 `registerButton_` 成员，其他函数才能在登录等待时禁用它、结束后恢复它。

`registerDialog_` 用于知道“注册窗口是不是已经存在”，`authenticationTimeoutMs_` 把同一份超时设置传给新窗口。默认仍是 10000 毫秒，测试可以传更短的值。

### 2.2 你现在就能验证

不需要启动服务器或数据库：

1. 运行客户端，填写 `http://127.0.0.1:8081`。
2. 点注册，应该出现注册框，而不是原来的不可用提示。
3. 点返回登录，应该回到原登录页。
4. 改成明显错误的地址 `hello` 后再点注册，应在登录页显示地址错误。

**观察点：能打开注册框只证明本地地址格式通过，不证明该地址上真的有服务器。**

## 3. 模块二：表单、成员变量和即时提示

**一句话：窗口保存输入控件，并在用户输入时提示明显错误。**

### 3.1 先认识头文件中的成员

| 成员 | 你可以怎样记 |
|---|---|
| `usernameEdit_` | 用户名输入框 |
| `passwordEdit_` | 密码输入框 |
| `confirmationEdit_` | 确认密码输入框 |
| `submitButton_` / `backButton_` | 注册 / 返回登录按钮 |
| `statusLabel_` | 提示文字 |
| `serverUrl_` | 打开表单时确定的服务器地址 |
| `submittedUsername_` | 本次提交的用户名副本 |
| `pending_` | 是否正在等待注册结果 |
| `client_` | 这个注册框使用的 ApiClient |

`Q_OBJECT` 支持类声明的 Qt 信号等元对象功能；`signals:` 声明通知接口，`private:` 下的普通函数是内部实现。先知道用途，不必一开始研究 Qt 生成代码。

### 3.2 创建输入框的代码怎么看

构造函数用一个 `field` lambda 复用“创建标签 → 创建输入框 → 放入布局”的步骤。

```cpp
auto field = [this, layout](const QString &title, const char *name, bool password) {
    auto *label = new QLabel(title, this);
    label->setObjectName("fieldLabel");
    auto *edit = new QLineEdit(this);
    edit->setObjectName(QString::fromLatin1(name));
    if (password) edit->setEchoMode(QLineEdit::Password);
    label->setBuddy(edit);
    layout->addWidget(label);
    layout->addWidget(edit);
    return edit;
};
```

- `auto field = ...`：保存一段可调用的代码。
- `[this, layout]`：这段代码可以用当前窗口指针和布局指针。
- `new QLineEdit(this)`：输入框是窗口的子对象，跟随窗口清理。
- `setObjectName`：给控件起稳定的名字，便于样式匹配和测试定位。
- `Password`：界面显示圆点；不是把内存里的密码加密。
- `return edit`：把新输入框的指针交给调用处保存。

`setPlaceholderText` 设置的是空框提示，不算用户已填写。`tr(...)` 让文字可以接入翻译，当前仍显示中文。

### 3.3 即时提示怎样发生

实际连接：

```cpp
connect(edit, &QLineEdit::textChanged, this, &RegisterDialog::updateHint);
```

按一句话读：**这个输入框的文字变化时，让当前注册窗口执行 updateHint。**

`updateHint()` 调用 `validationError(false)`，再把返回文字显示出来。它不会发 HTTP 请求。

当前文件中 `updateHint()` 的 `if (pending_) return;` 前有“上一个请求还没结束，不重复提交”的注释。准确理解应是：这里防止等待中的状态提示被输入提示覆盖；真正的重复提交检查在 `submit()` 开头。阅读代码时优先看函数实际做什么。

### 3.4 你现在就能验证

注册框刚打开时，不会立刻显示“用户名错误”。输入 `a` 后会提示用户名规则，改成 `demo_user` 后该错误消失。这个过程不需要任何服务器回应。

## 4. 模块三：validationError 检查输入

**一句话：返回空字符串表示当前检查没有错误，返回一段文字表示错误原因。**

### 4.1 为什么有 submitting 参数

实际代码中的用户名检查：

```cpp
const QString username = usernameEdit_->text();
static const QRegularExpression pattern(QStringLiteral("\\A[a-zA-Z0-9_-]{4,16}\\z"));
if ((submitting || !username.isEmpty()) && !pattern.match(username).hasMatch())
    return tr("用户名须为 4～16 位字母、数字、下划线或减号。");
```

`submitting` 表示“现在是不是准备正式提交”。

| 情况 | submitting | 用户名为空时 |
|---|---:|---|
| 刚打开表单、日常输入提示 | false | 暂不报用户名错误 |
| 点击注册 | true | 必须检查并拒绝空用户名 |

`||` 是“或者”，`&&` 是“并且”，`!` 是取反。上面的条件可读成：**如果正在提交，或者已经输入了用户名，那么用户名不符合规则时就报错。**

正则含义：整段输入只能包含 ASCII 字母、数字、下划线或减号，长度 4～16。C++ 字符串写两个反斜杠，是为了把一个反斜杠传给正则表达式。`static const` 让表达式对象保留并复用。

### 4.2 密码按什么长度检查

```cpp
const auto size = passwordEdit_->text().toUtf8().size();
if ((submitting || size > 0) && (size < 8 || size > 1024))
    return tr("密码长度须为 8～1024 字节。");
```

`text()` 取得 QString；`toUtf8()` 转成发给服务端时使用的 UTF-8 字节；`size()` 统计字节数。

例如 `12345678` 是 8 字节，`你好ab` 的 UTF-8 也是 8 字节。不能用看到的文字个数直接代替字节数。这里不自动去掉密码前后的空格。

### 4.3 确认密码怎么检查

```cpp
if ((submitting || !confirmationEdit_->text().isEmpty())
    && confirmationEdit_->text() != passwordEdit_->text())
    return tr("两次输入的密码不一致，请重新确认。");
return {};
```

确认密码用于防止用户输错，比较原始文字是否相等。`return {};` 在这个返回 QString 的函数中表示返回空字符串。确认密码只留在窗口，不发送给服务端。

**注意：函数按顺序返回第一个发现的错误。用户名不合法时，会先提示用户名，不会同时显示所有密码错误。**

### 4.4 练习输入表（不需要服务器）

每行操作前，先把其他字段填成合法值。

| 用户名 | 密码 | 确认密码 | 预期 |
|---|---|---|---|
| 空 | 空 | 空 | 点击注册后拒绝，提示用户名 |
| abc | 12345678 | 12345678 | 用户名太短 |
| demo_user | 1234567 | 1234567 | 密码太短 |
| demo_user | 12345678 | 87654321 | 两次密码不一致 |
| demo_user | 你好ab | 你好ab | 本地校验通过，随后尝试联系服务器 |

没有服务器时，最后一行出现网络失败是正常的，说明输入已通过并进入网络层。前三种输入错误不应进入 `ApiClient::registerUser()`。

## 5. 模块四：submit 和 setPending —— 最重要的一段

**一句话：先检查，再挂上“正在办理”的状态，最后发请求。**

实际代码：

```cpp
void RegisterDialog::submit()
{
    if (pending_) return;
    const QString error = validationError(true);
    if (!error.isEmpty()) {
        showStatus(error, "error");
        return;
    }
    submittedUsername_ = usernameEdit_->text();
    setPending(true);
    showStatus(tr("正在注册……可返回登录取消等待；取消不会撤销已完成的注册。"));
    client_->registerUser(serverUrl_, submittedUsername_, passwordEdit_->text());
}
```

| 顺序 | 这行在干什么 | 缺少它可能怎样 |
|---|---|---|
| `if (pending_) return` | 正在等上一次结果时，不再提交 | 从其他调用入口重复提交 |
| `validationError(true)` | 执行完整本地检查 | 把明显错误输入也发给服务器 |
| 错误时 `return` | 结束本次函数 | 只显示错误却仍继续发请求 |
| 保存用户名 | 记住本次请求对应的账号 | 结果处理依赖后来变化的输入 |
| `setPending(true)` | 进入等待状态、禁用提交和输入 | 用户不知道是否已提交，也可能重复操作 |
| `registerUser(...)` | 真正交给网络层执行 | 只有本地界面变化，没有注册请求 |

### 5.1 pending 与按钮是什么关系

```cpp
pending_ = pending;
usernameEdit_->setEnabled(!pending);
passwordEdit_->setEnabled(!pending);
confirmationEdit_->setEnabled(!pending);
submitButton_->setEnabled(!pending);
submitButton_->setText(pending ? tr("注册中……") : tr("注册"));
```

`pending_` 是程序内部状态；按钮禁用和文字变化是这个状态的界面表现。`?:` 是条件表达式：pending 为 true 就选“注册中……”，否则选“注册”。返回按钮没有禁用，所以等待期间仍能退出。

### 5.2 纠正一个容易混淆的地方

“空字符串也继续注册”属于输入校验或校验失败后漏写 return 的问题。`setPending(true)` 不负责判断空字符串。

下面是用于思考的**错误顺序，不是让你现在替换源码**：

```cpp
client_->registerUser(...);
setPending(true);
```

ApiClient 遇到无效地址时会立即 emit 失败信号，而不是发送网络请求。当前对象处于同一 GUI 线程，默认连接可以立即执行结果槽：

```text
pending_ 仍是 false
→ registerUser 立即报告失败
→ 结果槽执行 if (!pending_) return，忽略这次结果
→ registerUser 返回
→ setPending(true)
→ 界面开始等待，但这次结果已经被忽略
```

因此采用先设状态再调用。正常登录页已经检查地址，这个例子不一定通过普通点击就能复现；它解释的是代码对同步失败的正确处理。`emit` 不表示一定排队到以后执行。

### 5.3 用两个变量跟踪一次请求

| 时刻 | 注册框 pending_ | ApiClient authenticationReply_ |
|---|---|---|
| 尚未提交 | false | 空 |
| 本地检查不通过 | false | 空 |
| setPending(true) 后、post 前 | true | 空 |
| 请求发出 | true | 指向本次 reply |
| 网络完成回调刚开始 | true | 被 clear 清空 |
| 窗口接收到结果 | 被设为 false | 空 |

这里的 clear 只是清空指针，不是删除 reply；稍后由 deleteLater 安排删除。

## 6. 模块五：ApiClient::registerUser 发请求、接结果

**一句话：把输入变成 JSON 发出去，等回复后报告成功或失败。**

### 6.1 前半段：组织和发送

```cpp
if (authenticationReply_) return;
if (!validServer(serverUrl)) {
    emit registrationFinished(false, tr("服务器地址无效，请返回登录页修改。"));
    return;
}
const QJsonObject body{{"username", username}, {"password", password}};
auto *reply = manager_->post(request(serverUrl, "/api/v1/auth/register", false),
                            QJsonDocument(body).toJson(QJsonDocument::Compact));
authenticationReply_ = reply;
timeoutReply(reply, authenticationTimeoutMs_);
```

先检查这个 ApiClient 是否有认证请求在途，再检查地址，随后生成 JSON。用 QJsonObject 可正确转义引号、反斜杠，不需要自己拼接 JSON 文本。

`request(..., false)` 最后一个 false 表示这次请求不附加认证 token。新用户尚未登录，注册接口不应该要求旧会话。

三个 Qt 类型可以这样区分：

| 类型 | 含义 |
|---|---|
| QNetworkRequest | 收件地址、请求头等请求设置 |
| QNetworkAccessManager | 发起网络操作的对象 |
| QNetworkReply | 跟踪这一笔请求，之后读取响应 |

`post()` 返回 reply，不表示注册已经成功。随后函数会返回，GUI 事件循环继续工作。这里没有自己创建线程，也不需要 while 循环等响应。

### 6.2 后半段：连接 finished

实际连接的外形：

```cpp
connect(reply, &QNetworkReply::finished, this, [this, reply, username] {
    // 当前代码在这里解析响应、判断结果、发出信号。
});
```

把 connect 读成：**reply 完成时，在这个 ApiClient 仍然存在的条件下，执行括号里的处理。**

`[this, reply, username]` 保存了需要的指针和用户名副本。username 是副本，函数返回后仍可用于核对；不要改成 `&username` 引用局部参数。this/reply 保存的只是指针，不因此延长对象寿命。

### 6.3 成功需要满足什么

```cpp
const bool created = reply->error() == QNetworkReply::NoError && status == 201
    && error.error == QJsonParseError::NoError && doc.isObject()
    && !user["id"].toString().isEmpty() && user["username"].toString() == username;
```

六个条件：没有网络错误、HTTP 201、JSON 正确、根节点是对象、有用户 ID、返回用户名与提交一致。`finished` 只代表结束，失败和超时也会结束。

读取响应使用 `reply->isReadable() ? reply->readAll() : QByteArray()`：超时 abort 后响应设备可能已关闭，避免在关闭的设备上强行读取。

然后：

```cpp
reply->deleteLater();
emit registrationFinished(created, message);
```

安排释放网络结果对象，再通知窗口。整个函数不创建主窗口，也不把注册当成登录。

### 6.4 你应该能画出的时间顺序

```text
submit 开始
→ 调用 registerUser
→ post 发起请求
→ 建立 finished 连接
→ registerUser 返回
→ submit 返回
→ GUI 继续处理事件
→ 稍后网络请求完成
→ 执行 finished lambda
→ 发 registrationFinished
→ 注册窗口处理结果
```

## 7. 模块六：超时、错误分类与重试

**一句话：不能永远等，也不能把所有失败都说成密码错误。**

### 7.1 定时器的四步

```cpp
auto *timer = new QTimer(reply);
timer->setSingleShot(true);
QObject::connect(timer, &QTimer::timeout, reply, [reply] {
    reply->setProperty("requestTimedOut", true);
    reply->abort();
});
QObject::connect(reply, &QNetworkReply::finished, timer, &QTimer::stop);
timer->start(milliseconds);
```

1. timer 的父对象是 reply，请求对象释放时一起清理。
2. 单次定时器只触发一次。
3. 超时时先标记原因，再 abort 中止请求。
4. 如果请求先完成，停止定时器。

默认 10000 ms，即 10 秒。构造函数允许传入短超时是为了测试，不必真的等 10 秒。计时依赖 GUI 事件循环；如果加入阻塞循环，计时器也可能延迟，不能把它当成独立的硬实时线程。

### 7.2 为什么增加 requestTimedOut 标记

abort 后可能看到的是“操作取消”错误。提前设置这个属性，可以区分“超时触发的取消”和“用户关闭窗口触发的取消”。属性相当于给这笔 reply 附加一条说明。

### 7.3 错误判断顺序

先识别明确超时，再解释 HTTP 错误，再处理其他网络错误。因为收到 409/429/503 时，Qt 的 error() 也可能非零；一开始就把 error() 非零全部当作断网，会丢掉服务器给出的真实含义。

| 情况 | 当前提示重点 | 下一步 |
|---|---|---|
| 400/422 | 输入不符合要求 | 修改输入 |
| 413 | 内容过长 | 缩短输入 |
| 409 | 账号已存在 | 换用户名或登录 |
| 429 | 请求过多；显示可解析的 Retry-After 秒数 | 稍后重试 |
| 5xx | 服务暂不可用 | 稍后重试或检查服务 |
| 登录 401 | 账号或密码错误 | 修改凭据 |
| 超时 | 没有及时确认结果 | 重试，注意结果可能已落库 |
| 网络失败 | 联系服务器失败 | 检查网络和地址 |
| 成功状态但响应缺字段 | 无法确认成功 | 检查接口协议 |

这是当前代码覆盖的主要分类，不声称已经穷举所有 HTTP 状态。文案是本地固定文本，不把远端错误正文直接当 HTML 展示。

### 7.4 超时为何说“结果尚未确认”

服务器可能已写入用户，但成功响应没有到达客户端。本地超时无法自动撤销数据库 INSERT。再次注册遇到账号已存在，可以尝试用刚才的账号登录。

## 8. 模块七：收到结果后恢复控件

**一句话：先解除等待，再分别处理成功和失败。**

在注册构造函数中找到连接 `registrationFinished` 的 lambda，前半段实际代码：

```cpp
if (!pending_) return;
setPending(false);
if (!created) {
    showStatus(message, "error");
    return;
}
```

`if (!pending_) return` 只处理本窗口正在等待的结果。`setPending(false)` 放在分支前，成功、失败都恢复状态。

失败分支没有 clear 输入框，所以账号重复时可以直接改用户名，断网时可以恢复网络后再次点击。注册失败保留密码；登录提交时清空密码是原来已有的另一种行为，不要混淆。

成功后保存用户名、清空两次密码，再关闭窗口并发成功信号：

```cpp
const QString username = submittedUsername_;
passwordEdit_->clear();
confirmationEdit_->clear();
QPointer<RegisterDialog> guard(this);
accept();
if (guard) emit registrationSucceeded(username);
```

`accept()` 结束对话框，也可能触发外部结束处理。guard 用来确认对象仍存活，避免外部槽删除了窗口后还继续使用它。第一遍先理解成功路径，guard 的细节见下一节。

登录页接到 `registrationSucceeded` 后回填账号、清空登录密码、恢复密码遮蔽、提示登录。**这里没有创建会话，也没有进入主窗口。**

## 9. 模块八：关闭窗口和对象寿命

**一句话：用户已经离开，就不能再把旧回复交给已经销毁的页面。**

### 9.1 三种机制不要混为一谈

| 机制 | 解决的问题 | 不会做什么 |
|---|---|---|
| QObject 父子对象 | 父对象销毁时清理子对象 | 不代表可以忽略所有异步回调 |
| QPointer | 对象销毁后观察指针自动变空 | 不负责延长寿命或主动删除对象 |
| connect 的 context | 接收上下文销毁时断开连接 | lambda 里仅捕获 this 不等于设置 context |

当前关系：LoginWindow 拥有登录 ApiClient 和 RegisterDialog；RegisterDialog 拥有自己的注册 ApiClient 和控件；ApiClient 拥有网络 manager；timer 跟随 reply。

独立注册客户端隔开了不同对话框的请求。关闭旧窗口再打开新窗口时，不会把旧结果误当成新窗口这次注册的结果。

### 9.2 cancelAuthentication 的顺序

```cpp
if (!authenticationReply_) return;
auto *reply = authenticationReply_.data();
authenticationReply_.clear();
disconnect(reply, nullptr, this, nullptr);
reply->abort();
reply->deleteLater();
```

先断开 reply 到这个 ApiClient 的结果回调，再 abort。因为 abort 也会触发 finished；若先 abort，旧结果槽可能立即运行。这里不发注册成功或失败通知，表示用户主动离开后不再更新页面。

`deleteLater()` 是交给 Qt 在适当时机删除，不是此刻直接 delete。当前窗口正常失败则不调用 cancel；它通过 finished 收到原因并恢复表单。

### 9.3 done 和 reject 分别在哪

RegisterDialog 重写 `done(int)`，结束时取消等待、恢复状态、清空密码，再调用 QDialog::done。正常 accept/reject 结束路径都会经过它。

LoginWindow 重写 `reject()`，关闭登录页时取消登录请求。登录窗口在 main 中是栈对象，关闭后未必立刻析构；主动取消能防止它隐藏后又被迟到成功信号带进主窗口。

`WA_DeleteOnClose` 只用于 new 出来的注册框，不能照搬到 main 中的栈上 LoginWindow。此处也没有让主窗口既由 unique_ptr 管理又自行删除。

### 9.4 怎样验证

运行第 13 节的 `closingRegistrationDiscardsLateResult` 与 `closingAndDestroyingLoginDiscardsLateResult`。它们安排晚到的响应，再关闭或销毁窗口，检查不会回填错误账号、错误认证或崩溃。

测试通过证明了所覆盖的时序，不等于证明所有未来多线程或跨对象改造都自动安全。

## 10. 模块九：登录改动与主窗口门禁

**一句话：注册完成后还必须单独登录；只有认证结果能触发主窗口。**

原来的登录网络逻辑已存在，本次重点修改：

- 用 authenticationReply_ 替代 ApiClient 内仅供登录的 loginPending_，统一记录在途认证请求。
- 支持配置超时时间，识别超时原因，使用同一错误分类函数。
- finished 开始时清空在途状态，结果报告前安排删除 reply。
- 登录窗口等待时禁用注册入口；关闭时取消认证。

LoginWindow 自己的 loginPending_ 仍然保留，用于界面状态。不要误以为所有同名标记都被删除了。

登录成功仍要检查 HTTP 200、网络无错误、JSON 正确、64 位小写 hex token、有效且未过期的 expiresAt、非空用户身份。随后才走：

```text
loginFinished(true)
→ LoginWindow::handleLoginResult
→ authenticationSucceeded
→ main.cpp 构造并显示 MainWindow
```

main.cpp 本次只改注释，已有门禁逻辑保留。它把登录页的 ApiClient 交给主窗口继续使用，先 show 主窗口再 hide 登录页。登录页仍活着，因此持有的客户端和会话也仍活着。

| 信号 | 表示什么 | 能否直接进主窗口 |
|---|---|---|
| connectionFinished(true) | /health 连接测试成功 | 否 |
| registrationSucceeded | 注册响应确认成功 | 否 |
| authenticationSucceeded | 登录响应通过认证检查 | 当前 main 的入口 |

### 13.4 测试文件里先认识三个东西

```cpp
QSignalSpy result(&client, &ApiClient::registrationFinished);
QTRY_COMPARE(result.count(), 1);
QCOMPARE(peer.requests.size(), 1);
```

- QSignalSpy：记录信号发了几次和参数，像一个观察记录器。
- QTRY_COMPARE：允许事件循环继续处理，等异步条件满足再检查。
- QCOMPARE：立即比较已知结果。

不要在刚 post 后马上用普通 QCOMPARE 要求回复已经到达；异步操作需要等待。

HttpPeer 是测试用小服务器。`responses` 是预先安排的回复；`requests` 记录实际收到的请求。负数 delayMs 表示故意不回复，正数表示稍后回复，用来稳定验证超时和迟到结果。

测试用 120 ms 超时是为了快速检查；生产默认仍是 10 秒。QTimer heartbeat 在等待中还能触发，说明测试覆盖的网络等待没有堵住 GUI 事件循环。

## 15. 三条必须会自己复述的执行轨迹

### 15.1 密码不一致

```text
submit → pending 检查 → validationError 返回错误
→ showStatus → return
```

没有 post，pending 仍为 false，没有数据库操作。

### 15.2 服务器返回 409

```text
submit → 校验通过 → 保存用户名 → pending=true
→ ApiClient post → 请求返回 409
→ authenticationFailure 生成账号重复提示
→ registrationFinished(false, message)
→ 窗口 pending=false → 保留输入并显示错误
```

它与断网不同：服务器收到了请求并明确回应冲突。

### 15.3 用户等待中关闭注册框

```text
reject → done → cancelAuthentication
→ 先断开结果回调 → abort → 安排释放 reply
→ 清空密码 → 关闭并清理注册框
```

取消的是本地等待。服务端可能已经完成注册，因此重新提交可能收到 409。

| R4 | 再注册同名账号 | 显示账号重复，允许修改 | 409 日志与提示 |
| R5 | 密码不一致时点击注册 | 本地拒绝，无注册请求 | 本地提示、请求计数或断点 |
| R6 | 同一请求等待期间连续点击 | 一次请求 | 精确请求计数或服务端对应日志 |
| R7 | 服务不可达后恢复，再重试 | 失败后控件恢复，之后可提交 | 两次操作结果 |
| R8 | 等待中关闭窗口 | 不崩溃、不误回填、不意外打开主窗口 | 界面与日志；模拟测试可稳定复现 |

用户名使用 4～16 位允许字符，例如 `learn_001`。连续提交前注意服务端注册为进程共享每窗口 5 次，之前失败也会消耗额度；遇到 429 先等窗口恢复，避免把限流当作其他用例失败。

真实服务超时不必通过破坏数据库或停公共服务制造；优先使用本机模拟不回应的用例。自动化中存在“能恢复”的断言，比只观察一次失败更完整。

## 19. 掌握标准与常见误解

读完不要求你背全部 Qt API，但应能解释：

- pending 管等待，validationError 管输入；两者不能互相替代。
- post 返回不代表服务器成功，finished 也不代表成功。
- 同线程默认信号连接可能立即执行，emit 不保证异步。
- QPointer 观察寿命，不拥有对象；捕获 this 不自动保活。
- 返回/关闭取消的是本地等待，不自动回滚服务器。
- 注册成功、连接成功、登录成功是三个不同结果。
- client_registration_tests 使用真实 Qt 网络与窗口，但服务器响应是模拟的，不能证明真实数据库权限或写入正确。

最建议的学习顺序仍是：**先走通密码不一致，再走通 409，再走通超时，最后学习关闭时的对象清理。** 每次只理解一条路径，比同时看所有构造、样式、网络代码更容易。
